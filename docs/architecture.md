# Architecture

Parlora Hub is a Laravel application with a React front end, run locally
with Docker Compose for a single learner and built so it can be published
later without a rewrite. This page describes the system as it stands after
Phase 0 (the skeleton) and the boundaries later phases build on. Decisions
with their trade-offs live in [`docs/adr/`](adr/).

## Components

| Component        | Technology                                      | Role                                                               |
| ---------------- | ----------------------------------------------- | ------------------------------------------------------------------ |
| Web application  | Laravel 13 on PHP 8.5, Fortify                  | Routing, authentication, authorisation, server-side grading        |
| Front end        | Inertia 3, React 19, TypeScript, Tailwind 4     | Pages rendered in the browser from props sent by Laravel           |
| UI primitives    | shadcn/ui on Radix, themed by the design tokens | Buttons, inputs, dialogs, the sidebar                              |
| Database         | PostgreSQL 17                                   | Accounts and, from Phase 1, content, progress and attempts         |
| Queues and cache | Valkey 9, Laravel Horizon                       | Background jobs (the `redis` connection), with an admin-only board |
| Mail             | Mailpit (development)                           | Captures every email sent locally                                  |
| Runtime          | Docker Compose project `parlora-hub`            | The `app` service plus the three services above                    |

The `app` service is built from the project's `Dockerfile` and runs
`composer dev`: `php artisan serve`, Horizon, the log tail and Vite, together
([ADR 0002](adr/0002-php-environment.md)). The same image runs in CI and,
later, on the server. Every port is published on `127.0.0.1` only.

```text
browser ──HTTP──▶ app (Laravel + Inertia) ──▶ postgres
   ▲                     │        └──────────▶ valkey ◀── Horizon workers
   └── Vite (dev, HMR) ◀─┘                     mailpit ◀── outgoing mail
```

### Request flow

A request reaches a Laravel route; middleware authenticates it and
`HandleInertiaRequests` adds the shared props (the signed-in user, feature
flags, the locale and its translations). The route returns an Inertia
response naming a page under `resources/js/pages/`, and React renders it in
the browser. Route helpers for the front end are generated by Wayfinder from
the Laravel routes (`resources/js/routes/`, git-ignored).

Anything that decides access or grades an answer runs on the server. Page
props never carry solutions before the learner answers.

## Accounts and access

- Authentication comes from Fortify (login, password reset, two-factor,
  passkeys). `HUB_REGISTRATION_ENABLED=false` removes the registration
  routes, so the sign-up page returns 404 and its links disappear.
- `users.is_admin` marks administrators. It is never mass-assignable and
  never sent to the browser; it is granted or revoked with
  `php artisan hub:make-admin {email} {--revoke}`. Today it only opens the
  Horizon board (`viewHorizon` gate).
- `users.learner_ref` is an opaque UUID created at sign-up and never changed.
  It is the only identifier Hub will share with Parlora Tutor.

## Parlora Tutor boundary

[Parlora Tutor](https://github.com/Mvh18/parlora-tutor) is a separate
product: the voice-AI engine for calls and AI grading of speaking and
writing. Hub is the learner-facing product and uses Tutor **only through its
HTTP API**. It never imports Tutor code or reads Tutor's database.

- **Data ownership:** Hub owns identity, progress, attempts, the mistakes
  notebook and spaced repetition (FSRS). Tutor owns conversations, keyed by
  `learner_ref`.
- **Contract:** Tutor's `contracts/openapi.json` is the source of truth; Hub
  keeps a versioned copy for CI from Phase 6. The planned flows are in
  [INTEGRATION.md](INTEGRATION.md).
- **Configuration:** `config/parlora_tutor.php` reads `PARLORA_TUTOR_ENABLED`
  (default `false`), `PARLORA_TUTOR_URL`, `PARLORA_TUTOR_API_KEY` and
  `PARLORA_TUTOR_WEBHOOK_SECRET`. Nothing reads it yet: Phase 6 adds the
  `ParloraTutorClient` HTTP client and the signed webhooks.
- **Network:** the two Compose projects will share the external Docker
  network **`parlora-net`**, so Hub reaches Tutor by service name. The name
  is reserved; neither project declares the network until Phase 6.
- **Optional by design:** with the integration off, or with Tutor down, Hub
  keeps working; only calls and AI grading are disabled, with a clear
  notice. The test suite runs with `Http::preventStrayRequests()`, so any
  unplanned outbound request fails it.

## Design system

The brand's look is defined once, as **design tokens** in
`resources/css/tokens.css`: colours for the light and the dark theme,
radii (including the speech-bubble corners), shadows and the type scale.
`resources/css/app.css` maps them into Tailwind's `@theme` and the shadcn/ui
variables, so components use utilities such as `bg-surface`,
`text-ink-muted` or `bubble-bl` and never raw colour values.

- The tokens are the design source. The original mockups are reference
  material outside the repository, not something to copy styles from.
- Tests check every declared text/background pair against WCAG 2.2 AA in
  both themes, and reject hex values, colour functions and Tailwind palette
  colours in `resources/js`.
- Bricolage Grotesque (headings) and Figtree (UI and body) are self-hosted
  from Fontsource packages; no request goes to a third-party font host.
- Interactive targets are at least 44 px, primary buttons 48 px.

## Interface language

The interface is English-only, and every user-facing string lives in
`lang/en/*.php`, one file per area (`auth`, `nav`, `home`, `settings`, …).
`HandleInertiaRequests` shares the active locale's groups with React (all but
the server-only `pagination`, `passwords` and `validation`), resolved once
per locale. Components read them through `useTrans()`:

```tsx
const { t } = useTrans();
t('home.greeting.afternoon', { name: 'Alex' }); // "Good afternoon, Alex"
```

The helper supports Laravel's `:placeholder` and plural syntax and throws on
a missing key in development and tests. Oxlint's `react/jsx-no-literals`
rejects hard-coded text in JSX, and a Pest test checks that every key the
front end uses exists.

## Quality gates

| Check      | Command (inside the `app` service) | Covers                                                                               |
| ---------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| PHP        | `composer check`                   | Pint, Larastan (level 8), Pest with coverage ≥ 85 % and ≥ 95 % on gates and policies |
| JavaScript | `pnpm check`                       | Oxfmt, Oxlint, `tsc --noEmit`, Vitest                                                |
| Build      | `pnpm build && pnpm check:build`   | Production assets, fonts served locally                                              |

CI runs the same checks plus a Compose smoke test, dependency audits and
licence policy; a single required status, `ci-ok`, aggregates them.
